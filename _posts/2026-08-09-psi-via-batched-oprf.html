Private set intersection, made cheap: how KKRT16's batched OPRF works

8 August 2026 · ~12 min read

Two parties hold sets and want the overlap — without revealing anything else. The classic approach costs expensive public-key operations per element. Kolesnikov, Kumaresan, Rosulek and Trieu (CCS 2016) showed the overlap can be computed with nothing but fast symmetric-key operations, by turning every element into an unlinkable tag that only one party can verify. The cost: communication that grows with the size of the sets, not the product of their sizes.

I. Two rosters, one overlap

Two hospitals want to know which patients they share, without either learning who the other treats. A payroll provider and a bank want the list of employees who are also customers, without exposing the full employee roll. Ad platforms and data brokers want overlapping audiences without shipping their entire lists to each other. Each case is the same shape: two sets in, one intersection out, and nothing else about the inputs allowed to cross.

That last clause is what separates the problem from ordinary database work. If the parties could just show each other their lists, the intersection is a five-line join — which is exactly what the insecure approach does, and exactly what "private set intersection" (PSI) forbids. PSI is the primitive that computes the intersection of two private sets, learning nothing about the other party's set beyond the common elements.

PSI is used wherever two organisations hold identifiers over the same people and neither may reveal its own full list.

Now the question this note answers. Before reading the paper you might guess that computing an intersection of an n-element set and an m-element set must cost work proportional to the product n×m — every element of one set compared against every element of the other. The central fact of the whole OT-based PSI family, KKRT16 included, is that it doesn't. Understanding why it doesn't is what this note is for.

II. Safe tags, then compare inside bins

1. A tag only one side can verify

Imagine you want to check whether someone is on a list, but you may not show the list, and they may not say outright who they are. The trick: both sides agree to run every element through a one-way function — a scrambled fingerprint. If two elements are equal, their fingerprints are equal; if they differ, the fingerprints look like noise.

But a plain fingerprint is not enough, because the party computing it can check its own elements against the other party's fingerprints. So the function is keyed, and the key is hidden. Cryptography calls this an oblivious PRF (OPRF) — a pseudorandom function where one party (the receiver) learns the output for its own inputs but not the key, while the other (the sender) keeps the key but never learns which inputs it was applied to.

Spell out what that gives you. The receiver takes its element, feeds it into the OPRF, and gets a tag. The sender, holding the key, can compute the tag for any element of its choosing. Now the sender sends its tags — but these tags are useless to the receiver, because without the key the receiver cannot tell which element produced which tag. The receiver can only compare: does my tag for this element appear among yours? If it does, the element is shared. That single asymmetry — one side computes tags, the other can verify them but cannot reverse them — is the whole protocol.

That is the "oblivious" part. The remaining problem is the n×m one: comparing every receiver element against every sender element is quadratic. Hashing-to-bins is what fixes that, and it's the second half of the mechanism.

2. Batching: charging the whole thing to OT

An OPRF evaluated once on one element is already interesting. But KKRT16's headline move is that the tags for the entire receiver set are produced in one go, using oblivious transfer (OT) extension — a way to amplify a small number of base OTs into a large batch of them using only cheap symmetric-key operations. The paper's own accounting is blunt: realizing m OPRF instances costs roughly the same as realizing 3.5m ordinary 1-out-of-2 OTs, where "ordinary OT" already comes from a fast extension.

Why this matters: before OT extension, each oblivious transfer needed a public-key operation, so per-element work was heavy. After extension, the public-key cost is paid once (for the seed OTs) and every generated OT is cheap. KKRT16 inherits that speed and then improves on it by making the OPRF batched — one extension run produces tags for the whole set, so the cost per element is a handful of symmetric operations, not a signature or an exponentiation.

The thing to keep

KKRT16 is fast because it never needs a public-key operation per element. It pays for a few seed OTs once, then manufactures the tags it needs with symmetric-key work — which is orders of magnitude cheaper per element than the Diffie–Hellman-style approach.

3. Bins: turning quadratic into linear

Here is the mechanism's second half. The receiver doesn't keep its tags in one big pile. It first scatters its elements into a hash table with Cuckoo hashing — a hash scheme that guarantees each bin holds at most one element by evicting and reinserting on collision. The sender, by contrast, uses plain (simple) hashing: each of its elements is copied into every bin its hash functions point to.

Why the asymmetry? A shared element must land in a bin both parties check. If the receiver's element sits in bin h(x) and the sender's copy is also in bin h(x), the two tags meet there and match. Because the sender puts its elements in all candidate bins, a shared element can never be missed; because the receiver uses Cuckoo hashing, no bin ever holds more than one receiver element, so the comparison count stays tiny. The receiver gets one tag per bin; the sender sends the tags of all the elements mapped into each bin. A receiver element is compared only against the handful of sender elements in its own bin — not against all m sender elements.

The effect compounds. Because every bin holds a bounded number of items, the total comparison work — and with it the communication — is proportional to the number of bins, which is proportional to the number of elements. Matching happens inside bins with O(1) candidates per item, so the whole protocol communicates in the sum of the set sizes, not their product. A stash-free Cuckoo table for n elements uses on the order of 1.27n bins in a common 3-hash configuration, which is where the "n" in the cost formula comes from.

III. The arithmetic: what "fast" means

The paper is concrete about its performance, and the numbers matter more for what they imply than for themselves. On the authors' own implementation, the intersection of two sets of 2^20 (about one million) elements is computed in 3.8 seconds — on a single machine with the two parties simulated, single-threaded per party. The important detail is that this is independent of the bit-length of the items: 32-bit or 128-bit identifiers cost the same, because the tags the protocol moves are fixed-width regardless of the elements they came from. That bit-length independence was itself the improvement over the previous OT-extension PSI of Pinkas et al.

Here is the worked version of the reader test. Two sets of size n each. A naive all-pairs comparison needs n×n tag comparisons and, depending on the encoding, could force a party to send n×n of something. KKRT16's bins reduce that to n bins with a bounded number of tags per bin, so the bytes sent are proportional to n — the sum of the set sizes — with a small constant. Which part is inherent? The linearity is inherent to the whole hash-to-bins family: any scheme that splits both sets into the same O(n) bins and only compares within bins is going to be linear. The specific constant — how wide the bins are, how many hashes, the tag width — is a property of the particular construction and can be tuned.

There is a second half of the story that the headline speed undersells: OT-based PSI is fast, but it moves more bytes than Diffie–Hellman-based PSI. The speed advantage is real; the communication advantage is not. If your network is the bottleneck and your elements are short, the DH approach can win on total bytes. KKRT16 wins when the computation is the constraint, which makes it the usual choice for large-set workloads where both parties are on a fast LAN.

IV. Where this stops being true

1. The security model is semi-honest

The single most important boundary is the threat model. The whole construction is proven secure in the semi-honest model — the adversary follows the protocol faithfully and only inspects its transcript, trying to learn more than it should. That is a much weaker adversary than a malicious one who can send arbitrary messages. And the difference is not merely theoretical: a party that deviates can extract real information. SecretFlow's own documentation puts it plainly — KKRT16 "may be attacked in the malicious model," and it recommends using it as one-way PSI, where only one party learns the result.

Semi-honest means exactly what it says

If your counterparty could benefit from cheating — not just from watching — you need a maliciously secure protocol, and you pay for it. The entire speed story of KKRT16 is bought with the semi-honest assumption.

2. Set sizes are public

The protocol assumes the parties' set sizes are known. The hash table has roughly as many bins as elements, and the number of bins and transfers is visible to both sides, so the cardinalities are public inputs — what stays hidden are the element values themselves. If your use case treats "how many customers you have" as confidential, this is a leak you need to design around, not a subtlety the protocol handles for you.

3. The advantage is at scale

The speedup over prior work is reported on large sets of 128-bit items. On small sets the overheads — the seed OTs, the hashing, the round trips — are proportionally larger, and the gap narrows or inverts. "Faster than DH-based" is a claim about the regime the paper benchmarked, not a universal law. One independent Go implementation (Optable's) reports a roughly 100× single-core speedup (300 s vs 3 s) on a million-record match, which is the right order of magnitude to expect — but it is a vendor figure, not a peer-reviewed measurement, so treat it as magnitude, not precision.

IdeaCommon misunderstandingCorrect use
Semi-honest security "The protocol is secure; that's enough." It is secure only if parties follow the protocol. For adversarial counterparts, treat it as one-way or choose malicious security.
O(n) communication "So communication is tiny." It is linear, not constant — and it can be larger than DH-PSI's bytes. Linear beats quadratic, not nothing.
"Faster" "Faster everywhere." Faster at scale on computation-bound setups. On short elements with tight bandwidth, DH-PSI can win.

V. The counter-section: "it's just hashing, why is this a paper?"

By now you might be thinking: hash both sets, compare the hashes. Where's the cryptography? Anyone can hash a list and compare. This is the obvious conclusion a reader draws, and it is exactly wrong — the paper's content lives entirely in the word oblivious.

Try the naive version and watch it fail. Both parties hash their elements with a public hash function and exchange the digests. The parties can then compare — but they have revealed all their elements' hashes, and since the domain is enumerable (identifiers are phone numbers, IDs, emails), any adversary can brute-force every candidate identifier against the received hashes and reconstruct the whole set. The naive scheme leaks everything. That is not a PSI protocol; it is a broken one.

The fix is exactly the OPRF. The tags must be computed under a key the receiver does not have, so the receiver cannot brute-force the sender's tags — it sees random-looking values it can only compare, never decode. The sender's tags are verifiable by the receiver (equal elements produce equal tags) but not invertible, because the key is withheld. The hashing is the same hashing anyone could do; the obliviousness is what makes it private, and the obliviousness is what the batched OT construction supplies. That construction is the paper.

Our protocol uses a novel adaptation of 1-out-of-2 OT-extension protocols, and is particularly efficient when used to generate a large batch of OPRF instances.

Kolesnikov, Kumaresan, Rosulek & Trieu, Efficient Batched Oblivious PRF (CCS 2016)

Put plainly: anyone can hash; the paper is about how to get the privacy of a keyed hash into a form cheap enough to run a million times. That is the entire content of the result, and the batching is not a performance footnote — it is what makes the protocol affordable at all.

What this counter-section is not

It is not an argument that KKRT16 is weak. It is the opposite: an argument that the interesting part is the obliviousness, and that a reader who sees only "hash and compare" has understood a different, insecure protocol.

VI. Working rules for choosing and using it

01

Match the threat model to the relationship

Semi-honest security is the right fit for mutually-distrustful-but-following institutions; it is the wrong fit when one party has an incentive to cheat, because a malicious adversary can break it.

02

Budget for bytes, not just seconds

OT-based PSI is fast and chatty; DH-based PSI is slow and quiet. If bandwidth is your binding constraint, the faster protocol may still be the wrong one.

03

Price the cost by set sizes, not by element width

Communication grows with the number of elements and is independent of how long the identifiers are — so buy more cost when sets grow, not when IDs grow.

04

Treat a wrapped library as a binary, not a contract

An existing implementation (SecretFlow, libPSI, Optable's Go port) gives you the speed and the security model it was built with; verify the parameter defaults and the threat model before relying on them.

05

Expect linearity, and make sure it holds

If a vendor's "linear" protocol starts behaving quadratically on your data — many bins, deep Cuckoo failures, huge elements — something is wrong with the parameters, and the formula you rely on has broken.

Closing, briefly: the mechanism is a keyed, one-way tag per element, produced in a batch with symmetric-key work, compared inside Cuckoo-hashed bins so the cost stays linear. The strongest evidence is the paper's own: roughly 3.5 OTs per tag, and a million-element intersection in under four seconds. The boundaries are equally clear: it is semi-honest, set sizes are public, and the advantage concentrates at scale.

Practical summary

  1. PSI = compute the intersection of two private sets, revealing nothing else.
  2. An OPRF makes tags that one side can verify but neither side can decode.
  3. Hashing-to-bins cuts comparison work from O(n×m) to O(n) — communication follows the sum, not the product.
  4. KKRT16 is fast (3.8 s for 2^20) because it uses only symmetric-key ops after a one-time OT setup.
  5. It is semi-honest only: for adversarial parties, treat it as one-way or use maliciously secure PSI.
