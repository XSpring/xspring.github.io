    Chapter 5: Threshold Cryptography

    TL;DR. Never rebuild the key — let each stake produce a partial signature or decryption, then Lagrange-combine the parts.
    🎣 The hook The bank's vault key is now Shamir-shared 3-of-5 with receipts. To sign a transfer, the old workflow still says: "gather 3 shares, rebuild the key on one laptop, sign, delete." For five seconds, the whole key lives in one place — exactly the single point of failure we set out to remove.

    Prerequisites

    • Chapters 1–4: Shamir sharing, Lagrange, finite fields, Feldman/Pedersen commitments, DKG intuition
    • High-level idea of public-key signatures ("private key signs, public key verifies") — no formula needed

    By the end you will be able to…

    • Distinguish rebuilding-based vs threshold use of a shared key
    • Apply Lagrange-in-the-exponent to combine BLS partial signatures by hand on a tiny example
    • Explain why ECDSA thresholds are hard (and how modern libraries solve it) vs BLS triviality
    • Choose threshold decryption vs threshold signatures for a given deployment (custody vs sealed data)

    The foundational truth

    The strongest way to use a shared secret is to never assemble it.

    Shamir shares have a built-in homomorphism (structure-preserving map): linear combinations of shares are shares of the linear combination. That lets each holder act locally on their share — sign, decrypt — and publish only a partial result. The combiner (any party) Lagrange-interpolates the *results*, not the key.

    You know the pattern from Chapter 1's additive trick: add shares locally and the sum reveals the sum of secrets. Shamir generalizes this from addition to any threshold reconstruction in the exponent.

    A familiar bridge — the choir singing without a solo

    Imagine the vault key is a song only the full choir should sing, but no singer knows the whole melody. Call it the Choir Model.

    • Private key S → the full melody (never written down in one copy)
    • Partial signature / decryption → one singer humming their note for the current lyric (message or ciphertext)
    • Combine by Lagrange → the audience hears the full chord when t singers hum together — no one ever sang the whole tune
    • Public verification key → the program that says which chord is correct, without revealing how it was sung

    The key shift from Chapters 2–4: we move from "combine shares to get S, then use S" to "use shares to get partial uses of S, then combine uses."

    ⚠️ Before we build further — most people leave this bridge thinking…

    "Threshold crypto means splitting the private key file into three pieces and each server holds a copy of the same file format"

    This is wrong because each server would still hold the full key — that's replication, not sharing — and compromising one reveals everything.

    What's actually true: Each server holds a *different* Shamir point of the key's polynomial — useless alone — and the protocol combines *outputs* computed from those points, never the points themselves.

    Building the model, one piece at a time

    BLS threshold signatures — Lagrange in the exponent

    State

    BLS signatures (Boneh-Lynn-Shacham) make threshold trivial because the signing map is linear: signature σ = H(m)^S where H(m) is the hashed message in a pairing-friendly group and S is the private key. If S is Shamir-shared as polynomial f(x) with f(0)=S, then partial signature from holder i is σi = H(m)^{f(i)}. Combining t partials with Lagrange at zero in the exponent rebuilds the full signature:

    σ = ∏ σi^{ Li(0) }  where  Li(0)= ∏_{m≠i} (−xm)/(xi−xm)  mod q

    No holder ever learns S. Verification uses the same public key as a normal BLS signature — the verifier cannot tell it was threshold-built.

    Illustrate

    Demo with same numbers as Chapter 2 but in exponent: p=101 group order q=101, generator g, message hash H(m) as group element. Shares from f(x)=53+20x mod101 gave (1,73),(2,93),(3,12). Threshold t=2, take (1,73),(3,12):

    L1(0)= 3·inv(1−3)=3·inv(−2)=3·50=150 mod101=52  (from Ch.2)
L3(0)= 1·inv(3−1)=1·inv(2)=51          → check: 52+? Wait for t=2 only these two

Partial sigs: σ1 = H^73,  σ3 = H^12
Combined: σ = σ1^{52} · σ3^{51} = H^{73·52+12·51}=H^{3796+612}=H^{4408}
  4408 mod101 = 4408−43·101=4408−4343=65 … not 53? — because we mixed q.

Fix with consistent L for this pair: earlier Ch.2 gave L1=52, L3=50
  (we swapped indices; for pair (1,3): L1=3/(1−3)=3·50=52, L3=1/(3−1)=51)
  Actually 73·52=3796 mod101=59, 12·51=612 mod101=6, 59+6=65 ≠53.

The error is pedagogy: Lagrange for (1,73),(3,12) over mod101
gives L1= 3/−2 = −3/2 = 50? Let's recompute cleanly:
  L1(0)= (−3)/(1−3)= (−3)/(−2)=3/2=3·51=52
  L3(0)= (−1)/(3−1)= (−1)/2= −51 mod101=50
  73·52=59, 12·50=600 mod101=95, 59+95=154 mod101=53 ✓
So σ = σ1^{52}·σ3^{50}=H^{53}= correct full BLS sig.

    Toy correction matters: the arithmetic is exactly Chapter 2's Lagrange, now in the exponent. A choir of two singers humming H^{share} with Lagrange weights makes the full chord H^S.

    # Real library (py): partial = hash_to_curve(msg) * share
# Combined: sig = Σ Li·partial_i  (elliptic-curve scalar multiplication)
def combine_partials(partials, xs, q):
    sig = identity
    for (x,y), partial in zip(xs, partials):
        Li = lagrange_at_zero(x, xs, q)
        sig = sig + Li*partial   # additive notation for BLS G1
    return sig
    If the combiner can produce σ = H^S, can't they then extract S and become the single point of failure again?
    No. They see only σ = H^S (the signature for that message), not S. Computing S from σ and H requires a discrete log — believed hard in the BLS group. Each signature leaks only one exponentiation of S, not S itself. A new message gives H(m')^S, still not S.
    Each singer holds a different note of the melody; two notes weighted correctly make the true chord, but neither singer heard the whole tune.
    🛑 Pause & reflect

    BLS threshold felt almost automatic. Why don't we just use BLS everywhere and ignore harder thresholds like ECDSA/threshold RSA?

    Expert answerBLS needs pairing-friendly curves (BLS12-381) not yet universal in HSMs, blockchains, or legacy PKI. ECDSA/secp256k1 dominates Bitcoin/Ethereum and many HSMs. So we must threshold what the ecosystem already uses, even when the math is uglier — that's the next scaffold.

    When the math is not linear — ECDSA & threshold decryption

    State

    ECDSA signing computes (r,s) where s = k⁻¹·(H(m)+r·S) mod q with per-signature randomness k. Both inversion and multiplication of shared values require interaction — you cannot Lagrange-combine in one round as with BLS. Modern protocols (GG18/GG20, CGGMP21) solve this with additively-shared k, multiplicative-to-additive conversion (MtA), and a final combined s where no party learns k or S fully.

    Threshold decryption (e.g., ElGamal) is the mirror image: ciphertext (g^r, m·pk^r), each holder publishes partial decryption (g^r)^{f(i)}, combiner Lagrange-rebuilds pk^r and divides. Linear again — decryption is BLS-like, signing with ECDSA is not.

    Illustrate

    ElGamal threshold decryption, t=2: public key pk=g^S, encrypt m as (c1=g^r, c2=m·pk^r). Holder i with share f(i) publishes di = c1^{f(i)} = g^{r·f(i)}. With holders 1 and 3:

    L1=52, L3=50 as before (mod 101)
Combine: pk^r = d1^{52}·d3^{50}= g^{r·(73·52+12·50)}=g^{r·53}= (g^S)^r
Decrypt: m = c2 / pk^r

    Same Lagrange weights as BLS — decryption composes. ECDSA instead needs 6–8 rounds in GG18: share k, compute r via joint ECDH, then MtA to combine k⁻¹ terms without revealing k.

    Why can ElGamal decryption threshold with a single round, but ECDSA signing needs many?
    Decryption is one exponentiation by the shared key — linear in the share, so Lagrange-in-exponent works in one round. ECDSA mixes inversion and multiplication of two shared values (k⁻¹ and S), which are not linear — you need interactive multiplication protocols to keep both hidden.
    Some tunes can be hummed in parallel (BLS, ElGamal); others need the choir to rehearse back and forth (ECDSA).
    🔴 Deep dive Why GG18 needs MtA — the 30-second sketch

    After joint generation of random k split additively (k = k1+k2+…), parties need k⁻¹ and then s = k⁻¹(H+rS) without exposing k or S. The trick: convert additive shares of k and S into multiplicative shares via Paillier encryption (MtA — multiplicative-to-additive). Each pair exchanges encrypted products, adds them locally, and obtains an additive sharing of k·S which can be opened as k·S mod q, then multiplied by k⁻¹ shares. The security rests on Paillier hardness + VSS — no pure Shamir Lagrange alone suffices for ECDSA.

    In the wild

    Once signing moves to partials, custody changes shape.

    Custody without a single key. A typical exchange now runs 3-of-5 threshold ECDSA (CGGMP21 or GG20) across HSMs in different regions — no HSM ever holds the full signing key, yet any three can co-sign a withdrawal. An attacker who compromises one HSM learns only one Shamir point; a data-center loss takes two HSMs offline and the remaining three still sign. The quorum policy is the same hill from Chapter 2, but the melody never leaves the choir.

    Sealing data without a single decryptor. Joint ciphertexts (e.g., medical cohorts) are ElGamal-encrypted to a DKG public key; threshold decryption requires t analysts to co-decrypt aggregated results, not individual rows — the pattern Chapter 6 extends to full MPC. Vault's transit engine can be fronted the same way: the decryption happens as partials, combined only at the requester.

    Watch the key type. Bitcoin/Ethereum legacy addresses mandate ECDSA on secp256k1 — you pay the multi-round cost. Newer systems (Ethereum's BLS12-381 for consensus, threshold credentials) choose BLS precisely because one-round Lagrange suffices.

    Active recall — Question
    A 2-of-3 BLS deployment has partials σ1=H^73, σ3=H^12 (q=101). What is the Lagrange-combined full signature, and why does this not reveal the key?
    Answer
    With L1=52, L3=50: σ=H^{73·52+12·50}=H^{53}=H^S — correct, and S stays hidden behind discrete log of H^S.

    Where it breaks

    Threshold does not mean Byzantine-proof by default.

    ⚠️ Common misconception"Any t partials always give a valid signature." A single malicious partial (wrong Lagrange exponent) corrupts the combined result like the bad stake in Chapter 4. Production thresholds add VSS-style proofs: each partial comes with a zero-knowledge proof that it used the correct share (e.g., Schnorr proofs of equal discrete log). Without those proofs, a cheater can force invalid signatures and cause liveness failures.
    🚫 Edge caseThree traps: (1) Nonce reuse in ECDSA thresholds leaks S — the per-signature random k must be fresh and jointly generated; (2) Different curves have different orders — using p=101 demo moduli in production leaks; real q is ~2²⁵⁶. (3) Combining partials from different messages (mix-and-match) yields nonsense — each threshold operation is bound to one message/ciphertext.
    🔮 PredictBefore Chapters 6–7: signatures and decryption use the key once per operation. What if parties want to compute a function of *several* shared secrets together — say an average salary — without ever rebuilding any individual's salary? What primitive extends threshold from "one key, one use" to "many secrets, one joint function"?

    The whole picture

    The hook's five-second full-key window is unnecessary. The homomorphism that made additive shares sum to the secret — extended by Lagrange — lets each stake sign locally and publish a partial chord. The combiner Lagrange-weights those partials in the exponent and recovers the same signature a single key would have made.

    BLS-style schemes make this one-round because signing is linear in the key. ECDSA is not — it needs interactive MtA — which is why custody systems pay extra rounds for legacy curves and choose BLS where they can start fresh.

    The secret was never rebuilt. The melody was never sung solo — only the chord was heard. That pattern, from one secret to many, is multi-party computation.

    If you remember only one thing: Combine the *uses* of the key (partial sigs/decryptions) with Lagrange weights — never the key itself.
    🚀 Launch pad · one step beyond

    Build a 2-of-2 threshold Schnorr by hand

    Schnorr signing is linear up to a nonce: signature is (R,s) where R=g^k, s=k+eS with e=Hash(R,m). Design a 2-of-2 protocol where each party holds additive share Si (S=S1+S2) and per-signature nonce shares ki (k=k1+k2): each publishes Ri=g^{ki}, they combine R=R1·R2, compute e, then each publishes si=ki+eSi, combiner sets s=s1+s2. Show verification g^s = R·pk^e holds with pk=g^S, and argue why reusing (k1,k2) across two messages leaks S — mirroring classic Schnorr nonce-reuse leakage, now in threshold form.

    Stuck? Reveal a hint at a time.
    Hint 1 — reframeVerification is linear: g^{k1+eS1}·g^{k2+eS2}=g^{k1+k2}·g^{e(S1+S2)}=R·pk^e. The sum of partial s's is the full s. No Lagrange needed here because sharing is additive (n,n) — Shamir case would add Li weights.
    Hint 2 — key conceptNonce reuse: two equations s= k+eS and s'=k+e'S with same k give s−s'=(e−e')S → S=(s−s')/(e−e'). Threshold version leaks S identically — each party's ki reuse collapses even though S is shared.
    Hint 3 — setupExtend to 2-of-3 Shamir Schnorr: partial R's combine via Lagrange in exponent as with BLS, then signing uses Lagrange-weighted Si. The same reuse argument applies with weighted k shares — show why DKG per-signature nonce generation is mandatory.

    Glossary

    Threshold signature
    t partial signatures combine to a full signature valid under the single public key; no single party held the full private key. In the Choir Model: t hummed notes make the true chord.
    Lagrange in the exponent
    Combining rule σ=∏ σi^{Li(0)} or pk^r=∏ di^{Li(0)} — linear interpolation lifted into the group exponent. Choir weights applied to notes, not to singers.
    BLS (Boneh-Lynn-Shacham)
    Pairing-based signature where signing is one exponentiation — threshold is one round. Tune you can hum in parallel.
    ECDSA (Elliptic Curve DSA)
    Legacy signing with inversion and multiplication — threshold needs interactive MtA. Tune that needs rehearsal.
    Partial decryption
    di = c1^{f(i)} published by each holder; Lagrange combines to pk^r for ElGamal. Each singer's decryption note.
